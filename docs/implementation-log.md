# Implementation log: post-processor plugin system

What each phase of `docs/post-processor-spec.md` did, what it found, and what the next phase has to know. Newest at the end.

## Phase 0: golden files (commit f7f8d53)

Freezes today's G-code (v0.7.6) so that phases 1–2, refactors that must change no output, can prove it.

- **Matrix** (`tests/golden.rs`, module `matrix`; files in `tests/golden/`, described in `tests/golden/README.md`): 6 projects
  (`examples/projects/oval-sign` and the 5 built-in samples: name plate, box, relief, shaped relief, oval) × 5 dialects
  (GRBL, grblHAL, FluidNC, Mach3 / LinuxCNC, Marlin) × mm / inch × arcs off / on. Each case is written the way
  `putia-gcode -o` and File → Export write it: `pieces::generate_parts` with the summary header from `summary::add_header`, and
  also `split::generate_files` per tool where that makes more than one file. Every `.nc` has a `.notes.txt` with
  `Output.notes`. 280 + 280 files, 27.2 MB.
- **Byte-exact** comparison; a mismatch prints the file, the first differing line with context, expected and actual. A stale
  or missing file fails. `UPDATE_GOLDEN=1 cargo test --test golden` rewrites them.
- **Fixed machine**, so nothing depends on the local setup: the app's default machine, 300 × 200 × 60 mm, rapid 2000 mm/min,
  safe Z 5 mm, spin-up 2 s, no line numbers, G54 (the project's own `job.wcs`), no machine limits. Sample tool ids pinned.
- **Deterministic** over two runs, one and many test and rayon threads, another locale, and a regenerate.
- The 8 older GRBL snapshots in `tests/data/*.snapshot.nc` (`UPDATE_SNAPSHOTS=1`, with a coordinate tolerance as fallback)
  stay as they were.

## Phase 1: the IR inside the emitter

The emitter (`struct Em` in `src/toolpath.rs`) no longer writes text. It pushes events into a `Program` (new `src/program.rs`),
and a canonical renderer (new `src/program/render_canonical.rs`) writes the program as today's text. Gate: no golden file
changed after step 0 (`git diff --stat bb175ff -- tests/golden tests/data` is empty).

### Events and the lines they write

Every line of today's output comes from one event (or from the machine's start/end code, which has no event). The renderer
takes the dialect, units, work offset, line numbers, arcs and the start/end code from `Meta`.

| Today's line(s) | Event | Notes |
|---|---|---|
| `(PutiaCNC - GRBL)`, `(Stock … )` | `Comment { kind: Info }` | text without brackets; the renderer adds them |
| GRBL: `G21 G90 G17 G94 G54`; Mach3: `G21 G90 G17 G94`, `G40 G49 G80`, `G54`; Marlin: `G21 G90` and its two comments | `Setup` | units, WCS and dialect from `Meta`; Marlin's two operator comments are part of its setup block |
| the first `G0 Z…` (written by hand) | `Rapid { to: z }` at `meta.start_at` | no `Move` |
| `G0 …` / `G1 …` | `Rapid { to }` / `Feed { to, feed, write_feed }` | `to` holds only the axes written; `G1 F800` alone is a `Feed` with no axis |
| `(Pass n)`, `(Pass n, levelling lap)` | `Comment { kind: Pass }` | |
| `(Operation k: …)`, `(Repeat i of n)` | `Comment { kind: Operation }` | |
| `(Pen: the spindle stays off)` | `Comment { kind: Info }` | |
| `(Tool: name)` / `T# M6 (Tool #: name)` | `ToolChange { tool }` | Mach3 writes the `T` line, the others the comment; the name made plain ASCII by the renderer (`tool_label`) |
| `M3 S…` | `SpindleOn { rpm }` | |
| `M5` | `SpindleOff` | |
| `G4 P2` (spin-up) | `Dwell { why: SpinUp }` | written as given |
| `G4 P0.13` (pen-down dwell) | `Dwell { why: Requested }` | two decimals (`to_fixed(s, 2)`) |
| `M0 ; msg` / `M0 (msg)` / `M0 msg` | `Stop { message }` | GRBL family / Mach3 / Marlin (`marlin_stop`) |
| final `M5` (or Marlin's stop) | `SpindleOff` (or `Stop`) | |
| `G0 X0 Y0` and `M2` / `M30` / `(End of program)` | `ProgramEnd { park: X0 Y0 }` | two lines; the park has no `Move` |
| `G2` / `G3` | — | fitted on the text by the renderer; an arc line maps to the first event of the run it replaces |
| start / end code | — (`Meta.start_code`, `end_code`) | source `None` |

Renderer order, as the generator had it: events → arc fitting (with arcs off: only the trochoidal ranges, from the back; with
arcs on: everything) → start code before the event at `start_at`, end code before the last line → `marlin_comment` over all
lines → `number_lines`. The trochoidal ranges were line ranges; they are event ranges now (from 8 events before the loops, as
it was 8 lines), mapped to lines through the source map. In the program body every event is one line before fitting, so the
ranges are the same lines; only the setup block has more than one line, and if a range ever reached back into it, the
extra lines would be header and setup lines without X or Y, which the fitter passes through and which do not move its
position.

Rounding: the renderer divides the stored work-mm value by the units factor and rounds with `to_fixed`, the same floating-point
steps as `go()` did (`(x - ox) / ku`, `(sz_init + zt) / ku`, `fd / ku`).

### `Move.stop`: the event rule

Old rule (text): a move starts from rest when a line written since the previous move (from the first line, for the first move)
starts with `M`, `G4` or `T`.

New rule (events, `Event::halts`): a move starts from rest when an event since the previous move is `SpindleOn`, `SpindleOff`,
`Dwell` (either kind), `Stop`, or a `ToolChange` on Mach3 / LinuxCNC (where it is a `T# M6` command; elsewhere it is a comment
and the `Stop` before it is what halts). The two differ in one place only: Mach3's setup line `G40 G49 G80` starts with `G4`,
so the old rule counted the setup as a halt before the first move. On Mach3 a `ToolChange` (`T1 M6`) always stands between
the setup and the first move, so the result is the same.

Proof while working: a temporary `program::legacy_move_stops` recomputed the old rule from the rendered text and was asserted
equal to `Move.stop` for every output of the golden tests (every matrix and option case, every split and plug file, the 8
snapshots) and for random projects (`tests/random_projects.rs`, each project in all 5 dialects, mm and inch; 20 seeds in
the normal run, and 400 seeds in a release run: 394 projects generated, 6 refused with a message, so about 3,900 programs). A mutation (a tool change never halts) made the Mach3 pen cases fail. The helper and
the assertions were removed before the phase was finished.

### Deviations from the spec's IR

- `Meta` holds what the renderer needs today: `dialect`, `units`, `wcs` (already resolved by `Job::wcs_name`), `numbered`,
  `arcs`, `start_code`, `end_code`, `start_at` (event the start code goes before) and `troch` (event ranges of trochoidal
  loops). It has no job name, stock, machine id or used tools yet.
- `Event::Setup` is not in the spec: the setup block after the two header comments (the spec's `on_open`).
- No `OperationStart` / `OperationEnd`: operation text is a `Comment { kind: Operation }`. Phase 2 needs the markers for
  `on_section`; the place is the operation loop in `generate()`.
- `ToolChange` has no `next`. `ToolRef.number` is `u32`, the order of first use (as `select_tool` numbered tools);
  `length_offset` is always `None`; `name` is the raw name.
- `SpindleOn` has no direction (always `M3`).
- `Feed` has no `kind`, and has `write_feed`: the emitter's modal feed rule stays in the emitter (it forgets the feed at every
  `select_tool`, `select_pen` and `op_pause`, even when they write nothing, so a renderer cannot rebuild it from the events).
  A `Feed` can have no axis (`G1 F800`).
- No `Arc` event: arcs are still fitted on the text, in the renderer (spec: "until the port matches today's output exactly").
- `Xyz` is three numbers and a mask with accessors (`x()`, `y()`, `z()`, `get(i)`), not three `Option<f64>`, so an `Event` is
  48 bytes instead of 64.
- `Stop.optional` is always false; `CommentKind::Warning` is not used yet.
- `render()` returns the arc counts (for the notes) instead of `Rendered.extension`, `line_ending` and `notes`; the notes are
  still written by `generate()`. `Output` does not keep the source map yet.

### Dialect decisions still in the generator (phase 2's `Caps` to-do)

What left `Em` is the formatting of G-code words. These choices of *which events* to emit still depend on the dialect:

1. Spin-up wait: none on Marlin (`Em.spin` is 0) → `caps.dwell` / `caps.spindle`.
2. `spindle_on`: Marlin gets `Stop("Start the spindle at N rpm, then resume")` instead of `SpindleOn` → `spindle = Manual`.
3. `spindle_off`: nothing on Marlin → `spindle = Manual`.
4. Tool change (`select_tool`, `select_pen`): a `Stop` with the change message before `ToolChange`, except on Mach3 / LinuxCNC;
   Marlin's message starts "Stop the spindle and change tool…" → `tool_change = Manual | Atc`, `spindle`.
5. `op_pause`: on Marlin, with the spindle used, the message gets "Stop the spindle. " in front → `spindle = Manual`.
6. Program end: Marlin gets `Stop("Stop the spindle, then resume")` instead of `SpindleOff` → `spindle = Manual`.
7. The first comment names the dialect (`(PutiaCNC - GRBL)`).
8. The work offset is resolved by `Job::wcs_name` (Mach3 has 9 systems, Marlin 1, the others 6) → `caps.wcs_count`.
9. `Move.stop` counts a `ToolChange` as a halt on Mach3 only → follows `tool_change = Atc`.
10. Tool numbers are the order of first use on every dialect (only Mach3 writes them) → phase 3's tool table.

The `mach` flag still runs through `relief_op`, `photo_op`, `draw_op` and `rest_pass` only to reach `select_tool` and
`select_pen` (item 4); `Em` keeps `marlin` (items 1–3, 5, 6) and `mach` (item 9). Not a dialect branch, but worth knowing:
the pen-down dwell is a `G4` on every dialect, Marlin included.

### `program` and `lines` differ after summary, split and pieces

`summary::add_header` (the summary comments at the top, and renumbering when the job is numbered), `split::generate_files`
(`(File i of n …)`, `(Before you start…)`, `(After this file: …)`) and `pieces::generate_parts` (`(Stock` → `(Plug piece`,
`[replaces the main stock…]`) still edit `Output.lines` afterwards and leave `Output.program` as the generator made it. So for
every output of `generate_parts` and `generate_files` (which always add the header), `lines` holds more than
`render(&program)` writes, and the line indices differ. Phase 2/4: those texts become events (or the post renders them), so
that `lines`, `program` and the source map agree again.

(the renderer writes the words into one buffer; `go()` used to build each word with its own `format!`). The cost is memory:

the text), and cloning it takes 30 ms more. The GUI clones the output once per finished generation (for the checks thread)
and for the setup sheet; if that ever matters, `Output.program` can become an `Arc<Program>`.

### Traps for phase 2

- Keep the rounding order: work mm → divide by the units factor → `to_fixed` → `num`. Converting earlier changes digits.
- Do not rebuild the move list from the events without skipping the first lift (`meta.start_at`) and the park: they have no
  `Move`. A `Feed` with no axis has a zero-length `Move`.
- The emitter's feed rule (`write_feed`) is not modal on values: it forgets the feed at every tool selection and pause.
- Arc fitting depends on the exact text (3 or 4 decimals, the feed word on the first line of a run, I/J rounded by
  `arcs::fixed`, written by `arcs::txt`, which are not `to_fixed` / `num`). An IR fitter must reproduce that before the text
  fitter goes.
- The start code goes in before the event at `start_at`, after fitting; the end code before the last line (after the park,
  before `M2` / `M30` / `(End of program)`); both before Marlin's comment rewrite and numbering.
- `marlin_comment` rewrites every whole-line `(…)`, including the machine's start/end code, but not the summary header, which
  is added after `generate()`: Marlin files have a bracketed header today (frozen in the goldens).
- `pieces.rs` and `summary::describe` find the stock comment by its text (`(Stock `), which fails on Marlin: the `-plug` header
  keeps "Stock" (above) and a Marlin summary has no "Zero" row. Both frozen in the goldens.
- Mach3's `G40 G49 G80` starts with `G4`: anything that reads the text by prefix must not take it for a dwell.
- `summary::describe` reads the text (the `M3` line and the `G4` after it, `M0` messages, the last 6 lines): a post that changes
  those words changes the summary.

## Phase 2: the post engine and the built-in packages

The generator asks the job's post what the controller can do (`Caps`) and holds no dialect branches; a post engine renders the
program with a *post package* (TOML manifest, templates checked at load); the five built-in dialects are such packages, embedded
in the binary; the canonical renderer of phase 1 is gone. Arcs are fitted on the events. Gate: no golden or snapshot changed
(`git diff --stat main -- tests/golden tests/data` is empty).

### What moved where

- `src/post/mod.rs` (new): the `Post` trait, `Caps` (`ArcSupport`, `ToolChangeMode`, `SpindleCtl`, `DwellUnit`, `CommentStyle`,
  `wcs_count`, `max_line_len`; `Caps::wcs_name`, `Caps::tool_change_halts`), `PropDef` / `PropKind` / `PropValue`, `PostCtx`,
  `Rendered` (lines, source map, extension, line ending, notes, and the arc counts for the generator's notes), `LineEnding`,
  `PostError` (file, line, message with the fix). `number_lines` and `stop_message` live here now and are re-exported at
  `toolpath::` as before (`summary` and `replay` use those paths). `test_program(&caps)`: the fixed test program of the spec
  (every event kind, two tools, an arc, a stop), made the way the generator would for those capabilities.
- `src/post/manifest.rs` (new): `Package::load(file, src)`. `serde` with `deny_unknown_fields` everywhere and `toml::Spanned`
  for line numbers; the `format_version` is read first, on its own, so that a newer manifest is refused for its version and not
  for a key this engine does not know. Defaults for `[caps]`, `[format]`, `[words]`, `[modal]` and every handler.
- `src/post/template.rs` (new): templates parsed and checked once, at load, per handler: words, variables, filters, flags,
  properties, `?` lines, whole-line and inline comments, the whitespace that goes with a placeholder.
- `src/post/engine.rs` (new): `Package::render_program` (below).
- `src/post/text.rs` (new): `Format` (decimals, inch decimals, trimmed or padded, length), `push_num`, the filters
  `comment_text` (what `toolpath::tool_label` did; `tool_label` now calls it) and `plain_text` (what `marlin_stop` did to the
  message), `comment_line` and `machine_line` (what `marlin_comment` did, for any comment style).
- `src/post/builtin.rs` and `src/post/builtin/{grbl,grblhal,fluidnc,mach,marlin}/post.toml` (new): `Dialect` (moved from
  `program.rs`), `builtin(d)` (loaded once, `OnceLock`; a built-in that does not load panics, and the lint test fails first),
  `for_job(&job)`. grblHAL and FluidNC are GRBL's file with another name.
- `src/program.rs`: `Meta.dialect` is gone (the post is the dialect); new events `OperationStart { index, name }` (name = the
  operation's kind), `OperationEnd { index }` and `Arc(Box<ArcTo>)` (no generator emits it yet; `ArcTo` has `write_feed` like
  `Feed`); `Event::is_marker`.
- `src/arcs.rs`: the fitter's core is `fit_items(&[Item], dec, k, max_sweep) -> Vec<Fitted>` on numbers; `fit_arcs` and
  `fit_arcs_mapped` read text lines into the same items and write the arcs (same text as before). `xy` is public (the engine
  reads non-move lines with it), `max_sweep(degrees)`.
- `src/toolpath.rs`: `Em` has `manual_spindle` and `atc` from the caps instead of `marlin` and `mach`; the `mach` parameter of
  `select_tool`, `select_pen`, `rest_pass`, `relief_op`, `photo_op` and `draw_op` is gone. `generate()` takes the post with

- `src/model.rs`: `Job::wcs_count()` reads the job's built-in post (`caps.wcs_count`), so the GUI's work-offset choice and the
  summary's "Zero" row follow the same source. `DIALECTS` stays for the GUI; a test pins each post's name to its label.
  `Job::mach()` and `Job::marlin()` stay (the GUI's export window hides the work offset on Marlin); the generator uses neither.
- `examples/check_post.rs` (new): lints a package (a path or `builtin:<name>`) and prints the test program it writes; phase 4a
  turns it into `putia-gcode --check-post`.
- `docs/posts/authoring.md` (new): the package format with the GRBL built-in as the worked example, and the TX-35 sketch.
- `Cargo.toml`: `toml = "1"` (std, parse, serde; already in the lock through the GUI). `THIRD-PARTY-LICENSES.txt` lists `toml` and
  `serde_spanned` (now runtime dependencies of the core; the GUI had them only as build dependencies, which cargo-about skips),
  in the Apache-2.0 block of the other toml-rs crates (same licence text). `locales`: one new note string, with its Italian.

### The engine

`Package::render_program(&Program, &PostCtx) -> Rendered`, in the order the generator ran its steps before the IR:

1. **Arc plan.** With `Meta.arcs`, the whole program; else only the trochoidal ranges; nothing when `caps.arcs = none` (with a
   note). The events become fitter items: a `Feed` that gives X and/or Y and no Z is a cut (its F given = `write_feed`), any
   other move gives its X and Y, and any other event is rendered (scratch state) and its lines read the way the text fitter read
   them: a comment line gives nothing, another line the X and Y words in it (`arcs::xy`). An event that writes no line (the
   built-ins' operation markers) is not there for the fitter, so it does not break a run. The numbers are the post's: the X/Y
   format's `value()` (mm → output units → `to_fixed`), the I format's decimals for the centre. Fitting comes **before**
   rendering because a post with modal words must render the arcs in order (a run of modal `X… Y…` lines replaced after
   rendering by `G3 …` would leave the next modal line reading as an arc).
2. **Events**, in order, each through its handler; a fitted arc through `on_circular` at the event of its first cut (its X and
   Y are the fitter's end point and its I/J the fitter's centre, both already in output units), the cuts it replaces only move
   the tracked position. The engine keeps the full current position in work mm (`{X:park}`, modal and `always` axes, the centre
   of an `Arc` event), the text each modal word last wrote and the last motion code; it forgets the modal state at
   `OperationStart`, `ToolChange` and `Stop` (Fusion's `forceAny` at a section), which the built-ins never notice (their words
   are `as_given` or `always`, every motion code `always`).
3. **The machine's own lines**: the start code before the first line of the event at `Meta.start_at`, the end code before the
   last line, after the fitting so it never sees them; whole-line `(…)` in them written in the comment style (Marlin's `;`).
4. **Line numbers** (`N10`, step 10) over everything, then `caps.max_line_len` (a longer line is an error).

Safety rule: a `SpindleOn`, `SpindleOff`, `Stop` or (with `atc`) `ToolChange` that the package renders as no line at all is a
`PostError`, never a silent gap; so is a spindle event sent to a `spindle = manual` post, and an `Arc` event before X and Y are
known. Properties come from `PostCtx.props` (a missing key takes the default; a value of the wrong type is an error); the
generator passes none yet. `S` in `on_section_tool` is the speed of the `SpindleOn` that follows the change (before the next
move); `next_tool.*` come from the next `ToolChange` in the program (the IR has no `next`).

### Word modes, the feed and number formats

- **Axis words.** `as_given`: written exactly when the event's `Xyz` gives the axis, the emitter's raw-value rule as phase 1 kept
  it; the built-ins use it. `modal`: written when the formatted text differs from what the word last wrote (and after a reset,
  above). `always`: the full position on every move. The spec's `modal = true` is `mode = "modal"`; a word with neither is
  `always`.
- **The feed: `write_feed` kept** (the second option of the task). `Feed.write_feed` is the feed's "given" flag, like an axis in
  `to`; the built-ins' F is `as_given`, so F is written exactly where the emitter decided, identical by construction. The
  emitter's rule stays in one place (it needs it anyway: a cut that changes no axis and no feed is not pushed) with its resets at
  `select_tool`, `select_pen` and `op_pause`, even where they write nothing. Not chosen: a reset event plus a modal F in the
  engine. To be identical it would have to compare the raw values as the emitter does (a text comparison writes F once for 800.01
  and 800.04, both `F800`), it would duplicate the emitter's rule, and the reset events would land in the trochoidal windows. A
  user post's `modal` F compares the text and forgets at a section, a tool change and a stop, which needs no extra event.
- **Number formats** (`[format]`): rounding with `toolpath::to_fixed` (JavaScript's ties), then the shortest form exactly like
  `toolpath::num` (`trim = true`, "0" for -0) or padded decimals (`trim = false`: `X74.232`, `Z14.280`, `F2500.0`; never `-0.000`).
  `length = true` divides by 25.4 in inch output before rounding, with `inch_decimals`; the built-ins: xyz 3 / 4, feed 1 / 2,
  `rpm` and `seconds` not rounded (`S18000.5`, `P2`). The order work mm → output units → `to_fixed` → text is unchanged.
- **Dwells.** A requested dwell is rounded to 0.01 s in the generator (`to_fixed(w, 2)`, a value: the time estimate never counted
  it), so `on_dwell` prints one way (`seconds` not rounded); the spin-up wait stays as given.

### Open problems

- **Marlin's dwell unit.** Marlin reads `G4 P` as milliseconds; the built-in wrote the pen's dwell in seconds (`G4 P0.13`), as
  PutiaCNC always did and the goldens froze, so on Marlin the pen waited 0.13 ms. Fixed after phase 2 as a reviewed golden change:
  see "After phase 2: Marlin's dwell in milliseconds" below.
- **The fitter reads X/Y words in text.** To stay identical, the engine reads non-move lines with `arcs::xy`, as the text fitter
  did: a GRBL stop "M0 ; move X10 away" or a Mach3 line "T1 M6 (Tool 1: X5 bit)" sets the fitter's idea of X, and a run of cuts
  that follows before a move gives X again is fitted from that wrong start (its arc carries the fitter's end point, not the
  tool's). No golden and no random program showed a difference, but it is wrong in principle. Phase 4a: take the position from
  the IR only (a reviewed change; add a golden case that shows it first). The same goes for the fitter not knowing the position
  at the start of a range until X and Y have both been seen.
- **`caps.dwell = "none"` drops a requested dwell silently** (`{P}` has no value, so the line is left out). Only a user post can
  have it; it deserves a note.
- **User posts in inch.** Only formats with `length = true` are converted; the spec says user posts are mm only, so phase 4a
  should refuse inch output for a non-built-in package (or require `length` on the X/Y/Z/I/J/F formats).
- **The TX-35 sketch** shows what phase 4a has to settle: the generator's `SpindleOn` also reaches `on_command` (`M3 S18000` after
  the template's `S18000M03`), its `SpindleOff` before a change doubles `?stop_spindle_before_tool_change: M5`, `{Z:park}` writes
  the current height (the IR's park has no Z), and the tool numbers are the order of first use until phase 3.
- `caps.max_line_len` stops the export (an error), not a note; a long comment would block it. Revisit when a post uses it.
- Unchanged from phase 1: `summary`, `split` and `pieces` still edit the text after `generate()`, so `Output.lines` and
  `Output.program` differ for their outputs; the summary reads the text (the `M3` line and the `G4` after it, `M0` messages).

### Traps for phase 3 (tool numbers)

- **The built-in Mach3 / LinuxCNC is an ATC post** (`tool_change = "atc"`, no `G43`): it writes `T{tool.number}` with today's
  order-of-first-use numbers. The spec's "ATC: every used tool must have a number, else an export error" and "ATC without length
  offsets: warning" would break every Mach3 job or add a note to every Mach3 program (a golden `.notes.txt` change). Phase 3
  needs a way for Mach3 to keep order-of-first-use numbers and no warning (a capability, e.g. `tool_numbers = "first_use"`, or a
  rule that only applies to user posts).
- `ToolRef.number` is set in `select_tool` / `select_pen` from `ToolSt.ids` (order of first use, pens included); `length_offset`
  is always `None`, so `{tool.offset}` is the number. Phase 3 resolves both there; the post only reads them.
- `on_section_tool` is driven by `ToolChange` events, not by `OperationStart` (an operation can have up to three tools: inlay,
  relief, rest pass). `next_tool.*` comes from the next `ToolChange` in the program; `{S}` there from the `SpindleOn` after it.
- With `atc`, a `ToolChange` that a package renders as nothing is an error (`must_write`); with `manual` it may write nothing
  (the stop before it carries the message).
- The operation markers are not counted in the trochoidal windows (8 events before the loops, markers skipped) and an empty
  operation has none (`Em::end_op` takes back an `OperationStart` with nothing after it). Any new event that writes no line for
  the built-ins must be skipped there too, or the fitter's window shrinks.
- Modal state is forgotten at `OperationStart`, `ToolChange` and `Stop`; the built-ins do not notice, a user post with modal
  words does (it writes them again).
- Template line numbers in errors assume no line-continuation backslashes inside a multi-line TOML string.

## After phase 2: Marlin's dwell in milliseconds

A change of its own, after phase 2 and outside the phases (which must not change output). The Marlin built-in wrote a requested
dwell (a Draw operation's pen-down rest, `OpParams::dwell`) as `G4 P<seconds>`, e.g. `G4 P0.13` for 0.13 s. Marlin's `G4`
reads `P` as **milliseconds** (`S` as seconds), so the machine waited 0.13 ms instead of 0.13 s. GRBL, grblHAL, FluidNC and
Mach3 / LinuxCNC read `P` as seconds, so their output stays as it was. Phases 0 to 2 froze it on purpose; it is fixed here.

- **The package** (`src/post/builtin/marlin/post.toml`): `[caps] dwell = "milliseconds"` (the engine passes seconds × 1000
  to `{P}`) and `P = { format = "milliseconds" }` with `milliseconds = { decimals = 0 }`. Whole milliseconds, because Marlin
  reads `P` as a whole number and seconds × 1000 is not always one in floating point (2.01 s gives 2009.9999999999998, which
  the `seconds = {}` format would print in full). The format is not a length, so inch output writes the same number.
  `on_dwell` stays `G4 {P}`. `G4 S{P}` (seconds) was not possible: a word writes its own letter, so that would be `G4 SP0.13`.
  Marlin's spin-up wait is never emitted (`spindle = manual`), so the pen's requested dwell is the only `G4` the post writes.
- **The 3D preview** (`src/replay.rs`): it read every `G4 P` as seconds, so `G4 P130` would have played as a 130 s wait per
  pen-down. It now reads `P` the way the controller does: milliseconds when the job's dialect is Marlin (`Job::marlin()`),
  seconds otherwise. This is a fact about the controller, from the model; `replay` still shares no code with `toolpath` or the
  posts. `summary` reads a `G4` only right after `M3`, which Marlin never writes, and `verify` does not read `G4`.
- **Goldens.** `UPDATE_GOLDEN=1 cargo test --test golden` changed two files, three lines each, all `G4 P0.13` → `G4 P130`:
  `pen/marlin-metric-noarcs.nc` and `pen/marlin-imperial-noarcs.nc`. `pen-tool-change/marlin-*` have no `G4` (no spin-up wait
  on Marlin, and that case sets no pen dwell); the `G4 P1` in `opt-start-end-code*/marlin-*` is the machine's own start code,
  written as given. No `.notes.txt` and no snapshot in `tests/data` changed.
- **Tests.** `post::tests::marlin_dwells_in_whole_milliseconds` (0.13, 2.01, 0.125 and 30 s, mm and inch, against the other
  built-ins' seconds); `marlin_metric` and `the_builtins_capabilities` updated; `tests/replay.rs`
  `a_pens_rest_is_read_in_the_unit_of_the_controller` (a pen rest of 0.25 s on GRBL, Mach3 and Marlin: the text, and a 0.25 s
  wait in the replay on all three; it fails with 250 s on Marlin without the replay change).

### Resolution (`toolnum::resolve`)

First match wins: (1) the machine's `tool_table` entry for the tool id (first entry if the table lists it twice), (2)
`Tool.number`, (3) order of first use, only with `tool_numbers = "first_use"`; first-use numbers skip every number taken by
a tool of *this program* resolved in (1) or (2) (a slot of a tool the program does not use is not taken). With `required`,
every tool that reaches (3) is named in one error. Two different used tools on one number is an error with every post,
GRBL and Marlin included (their text writes no number, but the setup sheet would list a clash). The length offset: the rack
entry's own when the number came from the rack, else `Tool.length_offset`, else the number.

**Where, and why not in `select_tool`.** The task asked for resolution in `select_tool` / `select_pen`. The skip needs every
tool the program uses, including the ones used later, which `select_tool` does not know yet. So `Em::tool_change` records
the tool (first use order, as `ToolSt.ids` did) with the old first-use number, and `generate` resolves all of them once the
walk is done, before rendering, and writes number, offset and source into each `ToolChange`. Nothing between reads the
number (`Move.stop`, the times and the trochoidal windows do not), and without numbers the result is the old order of first
use by construction (the goldens prove it).

**The machine.** Generation reads the project's copy of the machine (`ProjectData.machine`), as for every other machine
setting. The machine manager's list and the project's copy are two places: phase 4b's "Tool rack" tab must write the rack to
both (as `apply_machine_job` copies the other settings), or a project keeps an old rack.

**Split files.** Each file of a split program is generated on its own, so it is resolved on its own: with `first_use`, the
1/8" end mill is T2 in the whole `rack-first-use` program and T1 in its own file (golden). With rack slots the numbers are
the same everywhere; with `required` it cannot happen.

### The capability `tool_numbers`

`[caps] tool_numbers = "first_use" | "required"`, default `required` with `tool_change = "atc"`, `first_use` with
`"manual"`. The built-in Mach3 / LinuxCNC is an ATC post that sets `first_use`, so a Mach3 job without a rack keeps its
numbers and gets no new note (the trap of phase 2). The spec's "ATC without length offsets" warning comes only with
`required` (and more than one tool), so no golden note changed.

### The read-back description, and why it is independent

`verify::ReadBack` is plain data: comment style, I/J incremental, line numbers, motion codes always or modal, the dwell
unit, the decimals of X/Y/Z and I/J in the output units, and the tool numbers that are pens. The package builds it from its
manifest (`Post::read_back`), the generator adds `numbered` and `pens` from the program. `verify` parses the text itself and
uses nothing of `toolpath`, `post/engine.rs`, `template.rs` or `text.rs` (it formats its numbers with `{}`, not
`toolpath::num`), so a mistake in the code that writes the text is not repeated by the code that reads it. What changed in the
reader, none of which changes a hazard of any built-in program (goldens, snapshots, random projects):

- **Words without spaces** were already read (`words` scans letter + number), as were modal lines (the last G0-G3 stays);
  now tested on lines of `tests/data/tx35/vcarve/logo.nc` (read-only): `G1X74.934Y70.699Z8.200`, `X76.242Y69.401`, `M06T11`,
  `G43H11`, `S18000M03`, `M3S14000`, `G0Z14.280`.
- **G91** no longer ends the reading: relative moves are passed over (their axes unknown) until `G90`; **G28 / G30** make the
  position unknown. The TX-35 header `G0 G28 G91` … `G90` is read past instead of stopping everything at line 1.
- **G4 P** is added up in the post's unit (`Trace.dwell_s`).
- **Pens**: besides the `(Pen:` comment, an `M6` with a pen's tool number (`ReadBack.pens`) sets the pen state, for a post
  that writes no comments.
- Comments: `(…)` and `;…` are read as comments in every style (controllers read both; the GRBL built-ins write `M0 ; message`
  with the paren style). The style is in the description for the pen rule and for later.

`read` reports `Fact`s in one pass (T, M6, spindle on/off, G43 H, a move in another frame, each move with its line, text,
from/to in mm, centre, whether it wrote a motion code, spindle and pen state); facts of a line come before its move, as a
controller runs them. Hazards, cross-check and ATC checks all come from this one pass.

### The motion cross-check (`crosscheck::Checker`)

Inside `generate()`, on the post's lines (before `summary::add_header`, `split` and `pieces` add text; each split file and
plug piece is generated separately and checked on its own). The program's motion events are walked in order: `Rapid`,
`Feed`, `Arc`, and the `ProgramEnd` park (the first lift and the park have no `Move`, so the events are the reference).
Pairing is by order; the source map is used only to pass over the machine's own start and end code (lines with source
`None`, which no event describes); axes such a line moved count as unknown until a post line writes them again, and a note
says when the machine's code has moves.

- A text move matches the next program move when every axis both know is within the tolerance, every axis the event gives is
  in the text, and both are rapids or both cuts.
- A program move that goes nowhere at the output's resolution may be missing (a feed-only `G1 F800`, a modal word that does not
  change); a text move that goes nowhere may be extra (`G0{Z:park}`).
- A text arc against an `Arc` event: one for one, end, centre (I/J tolerance plus the start's) and direction. A text arc
  where the program has cuts is a fitted arc: it takes the program's cuts one by one, each on the arc within the fit
  tolerance and going its way (the sign of the cross product, allowing `r × fit`), until one ends where the arc ends.
- With `motion_always` (every built-in), a move line without a motion code is an error.
- Tolerance per axis: `0.5 × 10^-decimals × k + 1e-9` mm (0.0005 mm for 3 decimals, 0.00127 mm for 4-decimal inches). The fit
  tolerance: `arcs::ON_CIRCLE` (0.005 mm, the fitter's own: it puts the rounded points that close to a circle through the
  rounded start) `+ √2 × (axis + 2 × ij)` (the program's point against its rounded form, and the text centre rounded on each
  axis, which moves both the centre and the radius measured from the start).
- The first mismatch is the error: `G-code line N (text): the text goes to X… Y… Z…, but the program's next move is a cut to
  X… Y… Z… (mm). Export stopped: …`. A program move left over at the end (one that goes somewhere) is an error too.

### The ATC checks (`verify::AtcCheck`)

When `caps.tool_change = "atc"`, on the same facts, blocking like the cross-check:

- with `stop_spindle_before_tool_change` on (`PostCtx.props`, else the package's default; false when the package has no such
  property): no `M6` while the spindle runs (an `M3`/`M4` with no `M5`/`M2`/`M30` since);
- with `caps.length_offset`: after every `M6`, a `G43` whose `H` is that tool's `ToolRef.offset()`, before the first line that
  writes Z (a `G53` machine Z, `G53 G0 Z0`, is not a work Z move and is allowed);
- the spindle runs before every cutting move (G1-G3), except while a pen draws (the pen rule);
- the `T` in effect at the k-th `M6` is the k-th `ToolChange`'s number, there are as many `M6` as `ToolChange` events, and every
  `T` word is a number of one of the program's tools. "Each T word in order" taken literally would refuse a pre-selected next
  tool (`T{next_tool.number}` after `M6`, the spec's `preselect_next_tool`), so a stray `T` is checked against the program's
  tools instead.

The built-in Mach3 passes all of them unchanged (no property, `length_offset = false`; its pens are told by the comment).

### Open problems

- **Split files and first-use numbers**: each file is numbered on its own, so with `first_use` a tool can be T2 in the whole
  program and T1 in its own file (`rack-first-use` shows it). Harmless for Mach3 today (it numbered this way before), but
  worth a note in phase 4b's export window when a split ATC job has tools without slots.
- **`ToolChange` events of split files** say nothing about the other files' tools; the setup sheet reads the whole program and
  the plug pieces, so its slots are the whole program's.
- **The source map decides which lines are the machine's code** for the cross-check. The engine writes it, not the templates,
  so a package cannot lie in it; a Rhai post (phase 5) must not be able to set it either.
- **`G53` and `G28` lines** are not checked against anything (no event describes them). A post that writes `G53 G0 Z-50` would
  pass the cross-check; only the "nolift" hazard and the first work move's Z catch some of that.
- `AtcCheck` treats a `T` word in a stop message of a comment-free post as a tool selection (verify reads the text as a
  controller does, and `M0 T5 ...` would be read as `T5` by most controllers too). The built-ins put messages in comments.

### Traps for phase 4a

- **The TX-35 header.** `verify` now reads past `G0 G28 G91` (relative until `G90`) and `G53 G0 Z0` (Z unknown), but the
  "nolift" hazard fires for VCarve's `G54 X0 Y0` right after `G53 G0 Z0`, because a machine-coordinate lift says nothing about
  the work height. The spec's ordering (the first tool and `G0 Z…` before `G54 X0 Y0`) avoids it; keep that order.
- **`stop_spindle_before_tool_change`** is read by name from `PostCtx.props`, else the package's default. When the machine
  manager saves property values (phase 4a), pass them to `generate_with` (`generate` passes none). The TX-35's `M5` before
  `M06` is checked in the text, so the generator's own `SpindleOff` and the template's `?…: M5` may both be there; only one is
  needed.
- **`{Z:park}`** writes the current height: the cross-check treats that line as a move that goes nowhere. A park height of the
  machine (a real Z move at the end) needs an event (`ProgramEnd.park` with Z), or the cross-check refuses the text.
- **Pre-selecting the next tool** (`T{next_tool.number}` after `M06`) passes the T check (every T is a tool of the program, the T
  in effect at each `M6` is the right one); a pre-select that comes *after* the next tool's `M6` would not.
- **User posts in inch**: a package whose formats are not lengths writes mm numbers under `G20`; the cross-check refuses it
  (test `a_post_that_writes_mm_numbers_in_an_inch_program_fails`), so phase 4a's "refuse inch for user posts" is now a
  friendlier message rather than a safety need.
- `Post` has a new required method `read_back`; any new `Post` implementation must describe its text.
- The GUI must keep the machine list and the project's machine copy in step for `toolTable` (phase 4b), as for every other
  machine setting.
